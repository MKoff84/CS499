Artifact Description

The artifact I selected for this enhancement is my Pirate Intelligent Agent project, originally developed in CS 370: Current/Emerging Trends in Computer Science. The project uses Python and TensorFlow/Keras to apply deep Q-learning to a maze-navigation problem. The goal is to train a pirate agent to move through an 8-by-8 maze and reach a treasure location. In the original assignment, the maze environment and experience-management classes supported the learning system, while the primary portion I completed was the deep Q-learning training implementation. At that stage of the program, my main focus was understanding reinforcement learning and getting the intelligent agent to learn from its interactions with the environment.

I selected this artifact because it represents an important part of my development in artificial intelligence, but looking at the project now also showed me how much my approach to software development has changed. The original version was centered around a Jupyter Notebook with supporting Python files. It demonstrated the reinforcement-learning concepts required for the course, but much of the training workflow, configuration, and application logic was closely connected. For this milestone, I wanted to preserve the purpose of the original project while redesigning the software around the algorithm so that the application would be easier to understand, test, maintain, and expand.

Justification for Inclusion and Enhancement

The Pirate Intelligent Agent is a strong artifact for the Software Design and Engineering category because the enhancement required more than cleaning up code or adding comments. I refactored the original project into a modular application with separate components for configuration, the maze environment, the learning agent, replay memory, and the training process. A standalone main.py file now serves as the application entry point instead of requiring the project to be executed through a sequence of notebook cells. This separation of concerns makes each part of the application responsible for a specific task and reduces the amount of coupling between the reinforcement-learning algorithm and the rest of the software.

Several additional changes improved the quality and reliability of the artifact. Training parameters were moved into a validated configuration dataclass rather than being distributed throughout the notebook. The enhanced environment uses an Action enumeration to make movement choices clearer and less dependent on unexplained integer values. Replay memory was encapsulated in its own bounded component, and the neural-network agent now manages model creation, prediction, action selection, and target-network synchronization. The trainer coordinates these components and records reward, loss, and epsilon history for each epoch. Type hints, docstrings, input validation, exception handling, and a reproducible random seed were also incorporated throughout the design.

The enhancement also gave me an opportunity to correct defects rather than simply reorganize the original code. During the code review, I identified an invalid-action state issue in the original maze logic. The invalid branch assigned the state to a different variable from the one later stored, which could cause the environment to retain the wrong mode. The enhanced TreasureMaze implementation uses one consistent state variable and includes an automated test that verifies an invalid move is recorded as an invalid state. I also replaced the older Keras model-input construction with an explicit keras.Input layer and changed action selection so exploitation evaluates only currently valid maze actions.

Testing became a much more deliberate part of the enhanced design. In addition to integration testing in a notebook, I created a repeatable unit-test suite using Python's unittest framework. The final suite contains ten tests covering configuration validation, environment initialization and movement, invalid actions and maze values, replay-memory behavior, and neural-network state validation and prediction shape. All ten tests passed. The standalone application also completed a 15-epoch training run against the original CS 370 maze and produced a complete set of 15 reward, loss, and epsilon records. I do not view the resulting win rate as evidence of an algorithmic improvement because this milestone was focused on software engineering rather than optimizing the learning algorithm. Instead, the successful run demonstrates that the refactored components work together as a complete application.

Course Outcome Alignment

The completed enhancement remains consistent with the outcomes I identified in my Module One plan and primarily supports Course Outcomes 2, 3, 4, and 5. Course Outcome 2 is demonstrated through clearer source organization, documentation, type hints, a README, and the supporting narrative. These additions make the purpose and structure of the application easier to communicate to another developer or technical audience rather than requiring that person to interpret the original notebook workflow.

Course Outcome 3 is demonstrated most directly through the design decisions involved in refactoring the project. I had to consider the trade-offs between keeping the original implementation simple and creating enough separation to support future changes. Dividing the environment, agent, replay memory, configuration, and trainer into independent components adds some structural complexity, but it substantially improves maintainability, testing, and extensibility. Just as important, I preserved the original 8-by-8 maze when validating the enhanced application so that architectural changes were not confused with changes to the experimental environment.

Course Outcome 4 is demonstrated through the use of object-oriented design, dataclasses, enumerations, TensorFlow/Keras, bounded replay memory, automated testing, and structured metrics to transform the original academic reinforcement-learning prototype into a more complete software system. The application can now be launched independently through main.py and can support repeatable experiments without depending on the original notebook structure. This architecture also gives me a foundation for the later capstone enhancements without requiring another complete redesign.

Course Outcome 5 is partially demonstrated through a stronger security and reliability mindset. This project does not currently manage sensitive user data or expose a network interface, so the security risks are different from those of a web or database application. However, I added validation for configuration values, maze contents, starting positions, neural-network state dimensions, replay-memory operations, and actions. Invalid values are rejected with controlled exceptions instead of being allowed to propagate unpredictably through the program. These changes reduce opportunities for malformed input or unexpected state to produce incorrect application behavior. I do not consider Course Outcome 1 a primary outcome of this individual enhancement; the broader ePortfolio and later enhancements will provide stronger evidence for collaborative environments and decision support.

Reflection on the Enhancement Process

Looking at this project now, one of the biggest differences I see from when I originally created it in CS 370 is how I think about the software surrounding an algorithm. At the time, my primary goal was getting the deep Q-learning agent to function. During this enhancement, I approached the same project more as a software engineer and considered how the individual components could be separated, tested, validated, and extended without changing the purpose of the original application. That shift was probably the most important part of the enhancement for me. A working algorithm is only one part of a useful software system; the architecture around it determines how easily the system can be understood, verified, and changed later.

One challenge was separating responsibilities that had originally been convenient to keep together in the notebook. Moving configuration, environment behavior, replay memory, neural-network responsibilities, and training coordination into separate modules required me to think about what information each component actually needed. I also encountered smaller integration issues, including an incorrect folder location that initially prevented an agent module from being imported. Working through those problems reinforced the importance of package organization and testing components incrementally instead of waiting until the entire enhancement is finished.

Another useful lesson came from verifying the enhanced application against the original artifact. During development, the first 8-by-8 maze placed in the standalone application did not match the maze from my original CS 370 notebook. Rather than continue with an altered environment, I went back to the original artifact, verified the matrix, corrected main.py, and then reran the application. That experience reinforced an important part of refactoring: improving the internal design should not unintentionally change the requirements or behavior being preserved. The automated tests served the same purpose by giving me a repeatable way to verify important behavior after changes.

The final enhancement is significantly more maintainable than the original version and provides a better foundation for the rest of the capstone. At the same time, I intentionally did not turn this milestone into an algorithms or database enhancement. Improvements such as A* pathfinding, further experience-replay changes, and comparison of deterministic search with deep Q-learning are reserved for the Algorithms and Data Structures milestone. Persistent experiment storage is reserved for the Database milestone. Keeping those concerns separate helped me stay aligned with the enhancement plan while still designing the software so those capabilities can be incorporated later without tightly coupling them to the current reinforcement-learning implementation.

Database Enhancement Narrative

Milestone Four · Southern New Hampshire University · Matthew Biletnikoff

Artifact Description

The artifact I selected for the database enhancement is my Pirate Intelligent Agent, which I originally worked on in CS 370: Current and Emerging Trends in Computer Science. The original project used deep Q-learning to train an intelligent agent to navigate a maze and reach a treasure location. My primary work in the original project centered on implementing the deep Q-learning training process, while some supporting classes were provided as starter code for the course. I selected this artifact for my CS-499 ePortfolio because it has given me an opportunity to demonstrate how the same project can evolve as my understanding of software development has grown. During the previous capstone milestones, I first reorganized the project into a modular software architecture and then added A* and breadth-first search algorithms for deterministic pathfinding and algorithm comparison.

For this third enhancement, I added a relational database layer using SQLite. Before this enhancement, the application could generate training metrics and algorithm results, but those results existed primarily during the execution of the program. Once the program ended, there was no structured way to preserve individual experiments for later retrieval or comparison. The database enhancement changes that by allowing the application to persist information about deep Q-learning training runs as well as A* and BFS pathfinding experiments. This moves the project closer to the type of research and simulation software I am interested in developing professionally, where retaining experimental results is just as important as producing them.

Justification for Inclusion and Enhancement

I believe this artifact belongs in my ePortfolio because the database enhancement demonstrates more than simply connecting Python to SQLite. I designed a relational structure consisting of an experiment_runs table and an algorithm_results table. The first table stores information describing an experiment and, when applicable, deep Q-learning metrics such as epochs, wins, losses, win rate, average loss, final epsilon, random seed, and training duration. The second table stores deterministic pathfinding results such as whether a path was found, path length, nodes explored, total cost, and measured execution time. A foreign-key relationship allows multiple algorithm results to belong to a single comparison experiment. This became useful when I integrated the A* and BFS work from the previous milestone into the database enhancement.

I also wanted the database layer to demonstrate data integrity and security-minded development rather than simply storing values. The implementation uses parameterized SQL queries instead of constructing queries by concatenating values into SQL statements, which reduces SQL-injection risk. I added application-level validation where appropriate as well as database CHECK constraints, primary and foreign keys, indexes, foreign-key enforcement, and cascading deletion of related records. Database connections are handled through a context manager so successful transactions are committed, failed transactions are rolled back, and connections are closed when the operation is finished. These decisions demonstrate how database design affects the reliability of the entire application.

One improvement that became especially useful was connecting the database to the actual application instead of limiting the enhancement to isolated database examples. Running main.py now trains the DQN agent, records its actual metrics, runs the A* and BFS comparison, and persists those results. I then verified persistence by opening a new Python session and retrieving the records from the SQLite database. In the full 8-by-8 maze, A* and BFS both found a path with a length and cost of 24. A* explored 50 nodes while BFS explored 51. I do not consider the extremely small execution-time difference between the algorithms meaningful because of the size of the maze, but retaining the measurements gives the application a foundation for comparing larger experiments in the future.

Course Outcomes

The enhancement followed the database plan I established during Module One, particularly my goals of creating persistent experiment storage, developing a relational design, using SQL, validating stored data, and incorporating secure database interaction. As I worked through the enhancement, the design expanded slightly because the Algorithms and Data Structures milestone gave me another useful type of experiment to preserve. Instead of designing the database only around deep Q-learning, I created a related table that could also store A* and BFS results without treating reinforcement-learning metrics and deterministic pathfinding metrics as though they were the same type of data.

This enhancement most directly supports the course outcome involving the use of well-founded and innovative techniques, skills, and tools to deliver value. SQLite and Python's database functionality allowed me to transform temporary program output into persistent experimental data that can be retrieved and analyzed later. The enhancement also supports the security-focused outcome through parameterized queries, validation, relational constraints, foreign-key enforcement, and controlled transaction and connection management. It additionally contributes to the outcome involving the design and evaluation of computing solutions because I had to consider how different types of computational results should be represented and related without unnecessarily coupling the database to one algorithm. Documentation, naming, and the organization of the database interface also contribute to communicating the design in a way that another developer could understand and extend.

Reflection on the Enhancement Process

One of the most useful lessons from this enhancement was realizing that adding a database is not just about writing an INSERT statement. I had to think about what an experiment actually represents, which information belongs to the experiment itself, which information belongs to an individual algorithm result, and how those records should be related. Separating the parent experiment from its algorithm results gave me a cleaner design and made it possible to represent both the DQN and deterministic pathfinding portions of the project without forcing unrelated metrics into the same structure.

The testing process also exposed a problem that I probably would not have noticed through normal application use. My initial database tests created temporary SQLite databases, but Windows reported that some of those files were still in use when the tests attempted to remove them. That showed me that the database connections were not being managed as cleanly as I expected. I changed the connection handling to use a context manager that explicitly commits or rolls back transactions and closes each connection. After making that change, the complete automated test suite passed all 26 tests, including six tests specifically covering database persistence, relationships, validation, foreign-key enforcement, and cascade deletion. This was a good example of automated testing doing more than proving that the expected output was correct; it revealed a resource-management problem in the design and led to a better implementation.

Looking at the artifact now, the biggest improvement is that the three capstone enhancements work together instead of existing as separate demonstrations. The software-engineering enhancement created the modular architecture, the algorithms enhancement added new computational approaches, and the database enhancement now preserves the results produced by those components. That progression is important to me because it better reflects the type of AI, simulation, and scientific-computing systems I want to work on after graduation. A useful next step beyond the scope of this milestone would be to build reporting or visualization tools on top of the stored experiments so that larger groups of runs could be compared over time. For the current enhancement, however, the database provides a solid foundation for persistent, validated, and reproducible experiment tracking.
